## 核心结论（TL;DR）

> [!IMPORTANT]
> **这一宿不是“完全没进化”，而是“在随机抽签噪音里取得了局部真改进（防快攻、OB 追隐刀、2BG 预留），但同时被单局裁判漏洞和单链淘汰制反复放跑真修复、反复放进伪晋级，且底层的 1 矿运营 + 无二次侦察 + 负气卡兵死锁 + 兵种/微操天花板导致对 BananaBrain 全程 0 胜 32 负。”**

最关键的 4 个实证发现：
1. **“对手开局抽签”主导了绝大部分胜负**：96 局里对 `Steamhammer` 总共只赢了 **5 局**，其中 **4 局**（包括 `v4`/`v5`/`v6` 的晋级局）全都是因为 Steamhammer 恰好随机到了 `FastReaver`（4W/0L = 100%）；对 `PylonPuller` 的 `Cannon+DT` 开局全程 **0W/7L (0%)**。
2. **裁判机制存在结构性“新王样本量红利”漏洞**：Champion 复测输 1 局后胜率掉到 16.7%，任何 Challenger 只要单局随机抽赢 1 个对手就拿到 33.3% > 16.7% 直接晋级（哪怕总均分下降、把 `PylonPuller` 能力打丢）；反过来 `c18` 赢下唯一一场非 Reaver 的 `Steamhammer` 正常运营局（93.8 分）并修掉致命死锁 Bug，却因撞上 `PylonPuller` 的 0% 胜率 `Cannon+DT` 被一票否决。
3. **`v8` 体内仍残留至少 3 个已被挑战者发现并修过、却被连坐扔掉的致命 Bug**：尤其是 `train()` 里 `gas < type.gasPrice()` 在预留射程/科技气为负数时把 **0 气狂热者与农民彻底锁死**（`c17`/`c18`/`c19` 连续三次独立定位并修复，三次全被淘汰！）。
4. **对 `BananaBrain` 0W/32L 不是调参能跨过的**：二矿开出率仅 **19%**（获胜局是 **100%**），11–14 分钟仍停在 1 矿 3BG、峰值兵力仅 **10.3**（6 龙骑），被 BananaBrain 的多矿龙骑 + 运输机金甲 + 闪电直接碾平。

## 方向 2：复盘“裁判机制”——误晋级与误杀总账

检查 [scoring.py](../../app/rsi/scoring.py#L299-L396) 和 [v2_loop.py](../../app/rsi/v2_loop.py#L964-L1030) 后，发现了 **3 个精确的代码级机制漏洞**：

### 漏洞 A：“新王样本量不对称红利”（制造伪晋级）
`adjudicate_challenger()` 把 Champion 的**多局累计胜率**直接和 Challenger 的**单局 0/1 胜率**比较：
- 当 Champion 在某一对手上复测 1 局输掉，该对手胜率从 `100%` 跌到 `50%`，三对手均胜率从 `33.3%` 跌到 **`16.7%`**。
- 下一轮 Challenger 只要在**任意 1 个对手**上单局抽签赢 1 局，其三对手均胜率立刻是 **`33.3% > 16.7%`** -> 直接触发 `win_rate_improved` 晋级！
- 更致命的是：[scoring.py:L378](../../app/rsi/scoring.py#L378) 的防退化守卫条件写了 `and chal_wr <= champ_wr + 1e-6`——也就是说只要 Challenger 靠单局抽签“总胜率 > 老王”，**防退化守卫会被直接绕过**！

**实证误晋级案例**：
- **`c6 -> v4`（R7）**：`v3` 为 `Pylo 1/2 (74.6), Stea 0/1 (53.3), Bana 0/2 (46.7)`（均胜率 16.7%，均分 **58.2**）。`c6` 丢了 PylonPuller（45.0）、BananaBrain 惨败（15.7），仅靠 Steamhammer 随机到 `FastReaver` 赢 1 局，均分反而 **倒退 -6.83 分（51.4）**，却因 `33.3% > 16.7%` 直接晋级！
- **`c10 -> v6`（R11）**：同理，靠 Steamhammer `FastReaver` 赢 1 局、均分倒退 `-0.89`，PylonPuller 0 胜，依然直接晋级。结果 `v6` 后面复测打出 `Pylo 1/3, Stea 1/3, Bana 0/3`（均分跌到 41.6）的惨淡表现。

### 漏洞 B：“单局一票否决防退化”把真改进锁死
一旦 Champion 运气好在某个对手上凑够 `>=2 局` 且 `>=50%` 胜率（如 `v7` 对 `PylonPuller` 3W/0L），防退化守卫就会卡死所有“没在 PylonPuller 上 100% 抽赢”的挑战者：
- **`c18`（R19，最冤的误杀）**：同时修复了 **负气锁死狂热者 Bug**、**快攻期气上限 100→150 死锁**、以及 **炮台开局防隐刀**；打赢了整夜**唯一一场非 FastReaver 的 `Steamhammer` 正常龙骑运营局（M74，93.8 分）**。只因 PylonPuller 在 M73 恰好随机到了整夜 0W/7L 的 `Cannon+DT`，`c18` 的 `chal_wr = 33.3% == champ_wr`，触发 `regression_on_PylonPuller` 被直接淘汰！
- **`c17`（R18，胜负与局内分打架）**：首创修复 `train()` 负气死锁和 `Unbuildable_Location` 秒退，对 Steamhammer 激战到 36000 帧拿了 **89.6 高分**（超时平局 `inconclusive`，对手出了 103 叉 + 24 龙骑 + 4 航母），却因为 `inconclusive` 算 0 胜，被判 `win_rate_lower` 淘汰。
- **`c11`（R12）**：对 PylonPuller 赢（82.4）、对 BananaBrain 暴涨 +42.5 分（52.0 vs v6 的 9.4），仅因 Steamhammer 跌 1 局就触发 `single_opponent_score_drop` 淘汰。

### 漏洞 C：裁判没有扣除“对手随机套路方差”
96 局按对手随机套路拆开后，胜率呈现出极端的两极分化（见方向 4 表格）：**撞到 `Steamhammer:FastReaver` 基本白给分（100% 胜率），撞到 `PylonPuller:Cannon+DT` 基本必死（0% 胜率）**。1 局定生死实际上是在“给对手摇骰子”。

## 方向 3：复盘“模型改了什么”——为什么一直在拧小螺丝、零次动 Python？

### 3.1 23 次 Review 的算力与工具行为画像
从 `batch.json` 统计全部 23 轮 Agentic Review（模型：`claude-opus-5-5`，`review_reasoning_effort=high`）：
- **总耗时**：`12,094.7 秒`（**3.36 小时**，平均每轮 ~8.8 分钟）；
- **总 Token**：输入 **33.6M**（缓存命中 31.6M，94%），输出 **926.8K**；
- **工具调用分布**：`run_analysis`: 202 次、`read_policy`: 187 次、`edit_policy`: 118 次、`get_build_log`: 89 次、`get_frames`: 35 次、`check_candidate`: 26 次、`get_timeline`: **仅 8 次**、`read_engine_file`: **仅 6 次**。

### 3.2 为什么 23 轮一次都没动过 Python 指挥层？
1. **Prompt 显式引导优先改 C++**：[v2_loop.py:L77-L80](../../app/rsi/v2_loop.py#L77-L80) 明确写着 *"Prefer direct C++ capability evolution when the root cause is build order, scout-reactive tech switching, army composition, macro/expansion logic, or unit micro."*
2. **Python 层能力粒度太粗且在实战中几乎在“旁观”**：96 局里 Live LLM 总共 2,102 次决策，**1,673 次（79.6%）是 `keep_current`**，`llm_tool`（小队工具）使用次数是 **0**！Python 层只能发顶排粗粒度姿态键（`0=defend`, `9=safeRally`, `5=outer`, `6=main`, `-=reset`），根本管不了出兵、反隐、二矿和交战微操。
3. **盲区：模型几乎没查过 Live LLM 按键有没有帮倒忙**：23 轮只调了 8 次 `get_timeline`！而数据统计显示，**输局里 `lock_defense_fraction` 高达 0.22–0.24（赢局仅 0.00–0.03）**，Live LLM 在败局里按了 **106 次 `0 (defend)` + 97 次 `9 (safeRally)` + 30 次 `1 (evade)`**（赢局各仅 4 次、4 次、0 次）。这些姿态锁在劣势时大概率把部队锁死在家门口、甚至阻止扩张与反打，但模型从未深究过！

### 3.3 为什么单次改动只有 5–37 行，且陷入“土拨鼠之日”循环？
1. **不是看不清死因**：模型其实非常聪明，通过 `run_analysis` + `get_build_log` **精准定位出了几乎所有真实 Bug**（例如 `match-66@6840..8160` 负气锁 3BG、`match-48@3480` 野兵营、`match-87@8168` `theirs=0` 撞墙、`match-61@12240` 双 OB 挂机在主矿不管二矿隐刀）。
2. **是被“单局淘汰 + 局部 `edit_policy`”逼得不敢大改、又被迫反复重做**：
   - 模型在 23 轮里反复重复修同一个老毛病：
     - **主动反隐刀**：被连续尝试了 **9 次**（`c3`, `c5`, `c8`, `c9`, `c13`, `c15`, `c18`, `c20`, `c23`）——**全部被淘汰**！
     - **负气锁死狂热者 Bug**：被独立发现并修复 **3 次**（`c17`, `c18`, `c19`）——**全部被淘汰**！
     - **未侦察敌军战力下限 + 算入敌方炮台**：被尝试 **3 次**（`c3`, `c14`, `c22`）——**全部被淘汰**！
     - **脱战牵绳（防止追单个残兵进敌主矿白送）**：被尝试 **2 次**（`c14`, `c19`）——**全部被淘汰**！
   - 而且 `compact_for_review()` 的 `max_versions=12` 在后期会截断早期历史，加上单链淘汰后代码完全回滚到老 Champion，导致模型花了 3 个多小时在 **“发现真 Bug → 小修提交 → 单局撞到坏开局被淘汰 → 代码回滚 → 两轮后又踩坑重写”** 的死循环里空转！

### 4.3 机器人底座（`MacroBot.cpp`）的 5 层硬天花板

**结论：是的，现在的 `MacroBot.cpp` 底座存在清晰的“结构性天花板”，靠每次改 10–30 行小补丁根本不可能跨过 `BananaBrain`！**

1. **终生 1 矿症（最大硬伤）**：`expand2_frame = 8000`（5.5 分钟后才考虑二矿）+ `expand2_army = 8` + `!homeThreat` + `v6` 把 VR 排在二矿前面。实战中（如 `M86`、`M96`）打到 **18,000 帧（12.5 分钟）仍只有 1 矿 3BG、23 农民**，而 BananaBrain 早已 2–3 矿爆出 20–40 龙骑 + 运输机金甲 + 闪电。
2. **8000 帧后彻底“瞎眼”**：[v8/MacroBot.cpp:L609](./versions/v8/MacroBot.cpp#L609) 的 `scouting()` 在 `frame > 8000` 或遭遇 `homeThreat` 或残血后直接放弃侦察，之后**再也不派农民或 OB 去侦察敌方主矿/二矿/科技**！结果既看不到隐刀科技（导致 0W/7L 死于 `Cannon+DT`），也看不到敌方兵力（导致 `theirs=0` 盲冲）。
3. **兵种科技树残缺**：整个 `MacroBot.cpp` **完全没有闪电兵（High Templar / Psionic Storm）、白球（Archon）、和金甲运输机（Shuttle）**。后期纯靠地面叉龙 + 龟速步行金甲，面对 BananaBrain 的 **Shuttle-Reaver 伸缩空投 + High Templar 闪电 + 龙骑齐射**，单靠数量都换不过（战损比仅 `0.30`）。
4. **交战微操处于原始阶段**：
   - 指令冷却 `commandReady(u, 16)` 每 16 帧（0.67 秒）才能下一次命令，而 BananaBrain 是高频帧级微操；
   - **没有集火**（`c5` 加过但被淘汰）、**没有阵型/拉弧线/卡坡口**、**没有躲金甲炮弹和闪电**；
   - 龙骑拉扯条件 `u->getGroundWeaponCooldown() > 6` 机械后退 80 像素，对射龙骑时反而白丢射程输出；
   - 撤退/追击缺乏牵绳，经常 2–3 个单位追敌方残兵一路冲进敌方主矿白送。
5. **隐藏的生产死锁**：`train()` 中 `gas < type.gasPrice()` 在预留射程/VR/VB 气体导致 `gas < 0` 时，会把 0 气消耗的 **狂热者和农民也一并卡死**（`M54`/`M66`/`M72`/`M80` 实测触发 6–9 个连续状态周期，存矿 400–770、3BG 全闲置）。

## 方向 6：可观测性与归因能力升级清单

目前工程层（96 局零崩、FPS ~23.8）已经非常稳，但给**人和复盘模型**看的诊断信息还缺 4 块关键拼图：

1. **自动标注对手开局/科技标签（L0 `opponent_archetype`）**：
   - 在每局结束后，由 L0 直接从合法己方视野的 `observations.json` 提取标签（如 `EarlyZealotRush` / `CannonOpen` / `FastDT@frame` / `FastReaver@frame` / `DragoonMacro` / `Unscouted`），写入 `experiment-ledger.json` 和 `PROGRESS.md`。
   - **价值**：人和模型一眼就能区分“真变强了”还是“对手摇到了弱套路”；也能按套路维度追踪 0% 胜率死穴（如 `Cannon+DT`）。
2. **自动生成“致死时刻诊断卡片（Cause-of-Death Digest）”**：
   - L0 自动定位每局的 **3 个关键拐点**：
     1. 经济/生产异常窗口（存矿 ≥ 400 且 BG 空转帧数、负气锁死帧数、二矿推迟原因、卡人口帧数）；
     2. 兵力断崖时刻（连续 480 帧内兵力骤降 ≥ 40% 的坐标、敌我阵容、当时是否处于 `undetected` 或 `defend/retreat` 姿态锁）；
     3. Live LLM 按键干预审计（哪一帧按了 `0/9/1`，持续锁定了多少帧，期间是否漏掉反打/开矿时机）。
   - 直接放进 Review 的初始 `overview`，把平均 9 分钟 / 1.4M token 的盲搜式 `run_analysis` 压低一半以上。
3. **审查 Live LLM 指挥层的正负收益**：
   - 跑对照组（关掉 Live LLM 按键仅跑纯 `MacroBot` vs 开启 Live LLM）确认 `0 (defend)` / `9 (safeRally)` 到底是在救命还是在拖后腿（`lock_defense=0.24`）。
4. **突破“单链淘汰 + 150 行上限”的进化架构**：
   - **裁判改两段式（初筛 + 加赛确权）**：
     - 初筛（每对手 1 局，3 局）：不直接晋级！只要不崩溃、不降 FPS、且综合 L0 分 ≥ Champion - 3 或任意对手有突破（如赢下 Steamhammer/BananaBrain 或打平高分），即进入 **加赛确认池**；
     - 加赛确认（每对手补打到 **3 局，共 9 局**，按套路分层记录）：用 **Wilson 下界 / 贝叶斯胜率 + 均分** 与 Champion 同等样本量比较，彻底根除“1 局抽签晋级”和“1 局偶发输 PylonPuller 一票否决”；
     - 修复 `scoring.py` 中防退化守卫逻辑（只在确认赛多局样本下触发，禁止新王靠小样本绕过）。
   - **保留有效补丁 / 轻量分支合并（Patch Pool）**：
     - 允许 Reviewer 在 `overview` 里看到被淘汰版本的 **独立好补丁清单**，并开放一个 `read_candidate_diff(candidate_id)` 工具（只读历史候选 diff），避免反复重写、支持把好补丁合流进新候选。
   - **允许架构级重构轮次**：
     - 当连续 2–3 轮微调卡死在底座天花板（例如对 `BananaBrain` 0 胜），引入一次“架构升级窗口”（例如把 diff 上限放宽到 300–400 行，或在人工把 **2 矿节奏 + 二次侦察 + 基础微操/集火 + 闪电/运输机底座** 搭好后再让 RSI 自动精调）。
